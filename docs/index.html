Technical Guide

This guide is for the group to understand, run, and demo Cikgu, even if you've never touched Django or Oracle before. It covers the request lifecycle, the hand-written SQL data-access layer, session authentication, routing, templates, how to run the system locally, and a page-by-page walkthrough mapped to the grading rubric — for the code at src/cikgu-app-django/.

01Overview

Cikgu is a normal three-layer web application: a browser talks to a Python web server, which talks to an Oracle database. Nothing runs "in the cloud" — everything runs on your own machine. The actual course deliverable is the database design and its implementation (schema/cikgu/) — this app exists to demonstrate that design working end-to-end, not the other way around.

Every query in this app is hand-written SQL against the schema — there is no ORM generating SQL on your behalf — and the database itself, not application code, is where triggers, the reporting view, and the recursive query live. That single rule shapes almost every design decision documented in this guide: the data-access layer, the custom session authentication, even how flash messages are wired up.

This app is a Python/Django rewrite of an earlier Java/Spring Boot implementation of the same design, which has since been removed from the repository — src/cikgu-app-django/ is now the only application here. Where this guide contrasts a decision with "the Spring Boot app," that's design lineage, not a second codebase still sitting in the repo — see §13 for the full picture.

You do not need to be a Django expert to demo this. You need to know: how to start Oracle, how to start the app, and what each page proves about the database design. See the ERD above for the schema shape, or if you only have 10 minutes before the presentation, skip to §11 Demo script and §12 Ten queries.

02Architecture

Same three-layer shape as the Spring Boot app — browser, app server, database — with Django's request/response cycle and middleware chain standing in for Spring MVC's filter chain: 

┌─────────────┐        HTTP         ┌───────────────────────┐   oracledb (thin)  ┌─────────────────┐
│   Browser   │  ───────────────▶   │   Django (WSGI, 8000)  │  ────────────────▶ │  Oracle Database  │
│             │  ◀───────────────   │   cikgu / cikguapp      │  ◀──────────────── │  (Docker, 1521)   │
└─────────────┘     HTML pages      └───────────────────────┘    rows / SQL       └─────────────────┘

Request lifecycle

Every request passes through this chain (see cikgu/settings.py → MIDDLEWARE):

SecurityMiddleware
  → SessionMiddleware            (decodes the signed-cookie session)
  → CommonMiddleware
  → CsrfViewMiddleware            (validates {% csrf_token %} on POSTs)
  → CikguUserMiddleware           (cikguapp/middleware.py — reads session → request.cikgu_user)
  → MessageMiddleware              (flash messages, session-backed)
  → XFrameOptionsMiddleware
  → urls.py → view function        (often wrapped in @login_required / @role_required)
      → repositories/*.py           (hand-written SQL)
        → db.py                      (cursor helpers over django.db.connection)
          → Oracle (CIKGU schema)

Two things stand out versus the Spring Boot app's filter chain: there is no django.contrib.auth in that list — role checks happen in view decorators, not framework middleware — and sessions are signed cookies, not a database table, so nothing about this app's login state ever touches Oracle.

05Data-access layer

Everything funnels through four small helpers in cikguapp/db.py, wrapping django.db.connection.cursor() — Django's raw DB-API cursor, the same primitive the ORM itself is built on, used here directly instead: 

def query_all(sql, params=None):
    """Run a SELECT, return a list of dicts."""
    with connection.cursor() as cursor:
        cursor.execute(sql, params or [])
        return dictfetchall(cursor)

def query_one(sql, params=None):
    """Run a SELECT expected to return at most one row; None if empty."""
    ...

def scalar(sql, params=None):
    """Run a SELECT of a single column/row and return that one value."""
    ...

def execute(sql, params=None):
    """Run an INSERT/UPDATE/DELETE, return the affected row count."""
    ...

dictfetchall lower-cases Oracle's column names (which come back upper-cased, e.g. GOAL_TITLE) so repository code and templates read naturally as goal_title. Every repository function is a plain function that takes primitives and returns dicts or lists of dicts — no query-building abstraction, no model classes. A representative example, the recursive mentorship query (cikguapp/repositories/users.py): 

def mentorship_hierarchy():
    """Full mentorship tree via Oracle CONNECT BY PRIOR."""
    return db.query_all("""
        SELECT t.user_id, au.full_name, t.expertise, t.years_experience,
               t.mentor_id,
               (SELECT m.full_name FROM app_user m WHERE m.user_id = t.mentor_id) AS mentor_name,
               LEVEL AS tree_level
          FROM tutor t
          JOIN app_user au ON au.user_id = t.user_id
         START WITH t.mentor_id IS NULL
        CONNECT BY PRIOR t.user_id = t.mentor_id
         ORDER SIBLINGS BY au.full_name
    """)

Transaction demos

The two places the Spring app used @Transactional — registration (superclass + subclass row) and module creation (module row + LEAD assignment) — use Django's transaction.atomic() the same way, in cikguapp/services.py: 

@transaction.atomic
def register(full_name, email, raw_password, phone, user_type,
             education_background, parsed_skills, expertise, years_experience):
    """
    The APP_USER superclass row and the matching subclass row (LEARNER or
    TUTOR) are inserted in ONE transaction — if either insert fails, both
    roll back and no orphan superclass row is left behind.
    """
    if users_repo.email_exists(email):
        raise RegistrationError("An account with that email already exists.")
    ...
    user_id = users_repo.next_user_id()
    users_repo.insert_app_user(user_id, full_name, email,
                                auth.hash_password(raw_password), phone, user_type)
    if user_type == "LEARNER":
        users_repo.insert_learner(user_id, education_background, parsed_skills)
    else:
        users_repo.insert_tutor(user_id, expertise, years_experience)
    return user_id

Integrity races — a second co-teacher assignment landing at the same instant, a duplicate enrollment — are still caught the same way the Spring app caught DuplicateKeyException: the view wraps the write in try/except django.db.IntegrityError and turns it into a friendly flash message, trusting the database's unique constraints (modtut_one_lead_uix, the enrollment composite PK) as the actual source of truth.

Oracle date handling

HTML <input type="date"> values arrive as YYYY-MM-DD strings and get parsed to datetime.date objects with django.utils.dateparse.parse_date. But python-oracledb binds DATE columns cleanly from datetime.datetime, not a bare date — so db.to_oracle_date() lifts every date to midnight before it reaches a query, the one small Oracle-specific wrinkle this port had to handle that JDBC didn't.

The SQL console's guardrail

cikguapp/console.py is a line-for-line port of the Spring app's QueryConsoleService: strip a trailing ;, reject anything with a second statement, require the input start with SELECT/WITH, and reject a regex-matched list of DML/DDL keywords appearing anywhere in the statement — a guard against accidental DML from the demo console, not a defense against a malicious DBA-level user, same caveat as the original.

06Authentication & sessions

This is the biggest structural departure from the Spring Boot app. Spring Security supplies a UserDetailsService, a filter chain, and role-based URL matchers out of the box. Django's equivalent, django.contrib.auth, expects a real AUTH_USER_MODEL — an actual ORM-backed table — which this app's "no ORM" design rules out. So authentication here is a small, self-contained layer instead: cikguapp/auth.py.

How login works

  1. auth.authenticate(email, password) looks up app_user by email (case-insensitive) via db.query_one.
  2. bcrypt.checkpw() verifies the password against the stored password_hash — the same hash format Spring's BCryptPasswordEncoder writes, so seeded accounts and Spring-created accounts log in here unchanged.
  3. On success, auth.login_user() cycles the session key (fixation protection) and stores {user_id, full_name, email, user_type} in request.session.
  4. CikguUserMiddleware reads that dict into request.cikgu_user on every subsequent request.

How role checks work

Two decorators in auth.py replace Spring Security's URL matchers:

@role_required("TUTOR")
def dashboard(request):
    ...

login_required redirects to /login/ if request.cikgu_user is None; role_required(user_type) wraps it and additionally redirects home with a flash message if the logged-in user's user_type doesn't match — the direct equivalent of .requestMatchers("/tutor/**").hasRole("TUTOR").

No server-side session table, by design SESSION_ENGINE = "django.contrib.sessions.backends.signed_cookies" in cikgu/settings.py means the session payload lives in a cryptographically signed cookie, verified with SECRET_KEY on every request, never persisted server-side. Combined with no ORM models, this Django app never issues a CREATE TABLE of its own — every table it ever touches is one schema/cikgu/cikgu_install.sql already created.

django.contrib.admin, django.contrib.auth, and django.contrib.contenttypes are all absent from INSTALLED_APPS — none of them are needed once authentication doesn't depend on a Django-managed user table, and leaving them out keeps the "zero Django-managed tables" property honest rather than just implicit.

08Templates & messages

Thymeleaf's th:replace fragments become Django's native template inheritance. Three base templates replace fragments/layout.html:

  • layout_base.html — the bare <html><head> skeleton, links the shared stylesheet.
  • base.html — extends it, adds the nav bar (role-conditional links, driven by the cikgu_user context processor) and a {% block content %}.
  • base_auth.html — extends it with just the centered .auth-wrap shell, no nav — used by login.html/register.html.

Every content page is now three lines shorter than its Thymeleaf equivalent:

{% extends "cikguapp/base.html" %}
{% block title %}My Goals{% endblock %}
{% block content %}
    <h1>My learning goals</h1>
    {% include "cikguapp/_flash.html" %}
    ...
{% endblock %}

Flash messages → django.contrib.messages

Spring's RedirectAttributes flash attributes (msg/err) become Django's session-backed messages framework. MESSAGE_TAGS in settings.py maps Django's SUCCESS/ERROR levels onto the existing .flash.ok/.flash.err CSS classes carried over from the Spring app's stylesheet — so the stylesheet needed zero changes: 

MESSAGE_TAGS = {
    message_constants.SUCCESS: "ok",
    message_constants.ERROR: "err",
    message_constants.WARNING: "err",
}

_flash.html is then just:

{% for message in messages %}
    <div class="flash {{ message.tags }}">{{ message }}</div>
{% endfor %}

The mentorship tree indent

Thymeleaf built the tree's indentation inline with #strings.repeat(...). Django templates have no string-repeat filter, so that computation moved to the view (views/tutor.py:mentorship) — one line per node, using the same rationale as the reporting counts on the learner dashboard: prefer a fat view over template logic Django doesn't have a clean built-in for.

Feeding Chart.js safely

Thymeleaf's th:inline="javascript" becomes Django's json_script filter — the idiomatic, auto-escaped way to hand server data to client JS without building a string by hand: 

{{ chart_data|json_script:"chart-data" }}
<script>
  const chartData = JSON.parse(document.getElementById('chart-data').textContent);
  new Chart(document.getElementById('topModulesChart'), { ... data: chartData.values ... });
</script>

11Demo script for the presentation

The System Presentation item (30 marks) explicitly rewards the main function working comprehensively, navigation working, and extra features (graphs, a real backend). The ERD Understanding item (5 marks) rewards relating the ERD to the running system while you explain it — not just reading the diagram. Suggested order, roughly 10–12 minutes, one member per numbered section works well for a 5-person group:

  1. Registration + inheritance (~1 min) — Register a new Tutor live. Point at the ERD: "this one form writes to both APP_USER and TUTOR in one transaction — that's the disjoint specialization."
  2. Goals + browse + enroll (~2 min) — As a learner, create a goal, browse modules filtered by difficulty, enroll in one linked to that goal. Point at the ERD: "ENROLLMENT is the bridge between LEARNER and MODULE, and it carries the goal link."
  3. Module + co-teacher management (~2 min) — As a tutor, create a module (note you're auto-assigned LEAD), then add a co-teacher. Optionally, open the SQL console and try inserting a second LEAD row to show the unique index rejecting it — a nice unscripted "the database itself enforces this" moment.
  4. Progress update + trigger (~1 min) — Update a learner's progress; point out last_updated_at changed even though nobody wrote to it explicitly.
  5. Mentorship hierarchy (~2 min) — Show the full CONNECT BY PRIOR tree, then reassign a mentor and explain the recursive relationship.
  6. Reports (~1 min) — Show the chart and the behind-schedule table; tie it back to the original problem statement ("tutors couldn't answer these questions without a spreadsheet — now it's one page").
  7. SQL console — one query per member (~3–4 min) — This is where the individual ad hoc query marks come from. Each member should have their own query ready (don't all reuse the same one — the rubric explicitly rewards different kinds of SQL). Good picks from cikgu_queries.sql: the join, the NOT EXISTS, the HAVING, and the window function all look visually different and are easy to explain in 30 seconds.
Before presenting: run through §9 end-to-end on the machine you'll demo from, at least once, so nobody is debugging Docker live in front of the lecturer.

12Ten queries for the presentation

Ready-to-run queries for the ADHOC Query (10 marks) and 10 SQL Queries report appendix (20 marks — 2 marks each for a genuinely different kind of SQL, 1 mark if it's just a repeat with different literals) items in docs/project_rubrics.pdf. Each one is tagged with the lecture it demonstrates, so between them they cover every syllabus lecture that has something expressible as a runnable query — syllabus/Lecture 2 (relational model), 3 (ER modeling / recursive relationships), 5 (transaction management), 6 (relational algebra), 7 (query processing / subqueries), and 9 (data warehousing / OLAP). Lectures 1, 4, and 8 are architecture and process topics (three-level architecture, the SDLC, distributed DBMS) without a single query that demonstrates them — Lecture 4's DDL angle is already fully covered by schema/cikgu/cikgu_create.sql.

Where to run these: queries 1–9 are plain SELECTs — paste them straight into the app's SQL Console (/console/), which accepts exactly this. Query 10 is a genuine UPDATE + ROLLBACK transaction demo, so it won't pass the console's read-only guard by design (see §5's "SQL console's guardrail") — run it in SQL*Plus or SQL Developer instead.

1. Selection & projection — advanced modules over 10 hours

Lecture 6 · Relational Algebra (σ, π) Console

Which modules are ADVANCED difficulty and take more than 10 hours?

SELECT module_title, duration_hours, difficulty
  FROM module
 WHERE difficulty = 'ADVANCED' AND duration_hours > 10
 ORDER BY duration_hours DESC;

A single table filtered by WHERE (selection, σ) and narrowed to three columns (projection, π) — the two most basic relational algebra operators, in isolation.

2. Multi-table equijoin — who's enrolled in what

Lecture 6 · Relational Algebra (⋈) Console

Which learners are enrolled in which modules, and how are they progressing?

SELECT au.full_name AS learner, m.module_title, e.progress_score, e.status
  FROM enrollment e
  JOIN learner l  ON l.user_id = e.user_id
  JOIN app_user au ON au.user_id = l.user_id
  JOIN module m   ON m.module_id = e.module_id
 ORDER BY au.full_name;

A four-table equijoin walking the inheritance join (app_user↔learner) and the ENROLLMENT bridge entity in one statement.

3. Outer join — enrollments with or without a goal

Lecture 6 · Relational Algebra (outer join) Lecture 2 · Relational Model (nullable FK) Console

List every enrollment together with the goal guiding it, including enrollments with no linked goal.

SELECT au.full_name AS learner, m.module_title, g.goal_title
  FROM enrollment e
  JOIN learner l   ON l.user_id = e.user_id
  JOIN app_user au ON au.user_id = l.user_id
  JOIN module m    ON m.module_id = e.module_id
  LEFT JOIN goal g ON g.goal_id = e.goal_id
 ORDER BY au.full_name;

A LEFT JOIN keeps enrollment rows whose goal_id is NULL — an inner join would silently drop them. Ties directly to the ERD's dashed "guides (optional)" relationship.

4. Correlated subquery — learners with zero enrollments

Lecture 7 · Query Processing (subqueries) Console

Which learners haven't enrolled in a single module yet?

SELECT au.full_name, au.email
  FROM learner l
  JOIN app_user au ON au.user_id = l.user_id
 WHERE NOT EXISTS (SELECT 1 FROM enrollment e WHERE e.user_id = l.user_id)
 ORDER BY au.full_name;

A correlated NOT EXISTS subquery — re-evaluated per outer row, the classic "rows with no matching child" pattern that a join can't express directly.

5. Recursive query — the full mentorship chain

Lecture 3 · ER Modeling (recursive relationship) Console

Show the entire tutor mentorship hierarchy, indented by depth.

SELECT LPAD(' ', 2*(LEVEL-1)) || au.full_name AS mentorship_chain,
       t.expertise, LEVEL AS depth
  FROM tutor t
  JOIN app_user au ON au.user_id = t.user_id
 START WITH t.mentor_id IS NULL
CONNECT BY PRIOR t.user_id = t.mentor_id
 ORDER SIBLINGS BY au.full_name;

Oracle's CONNECT BY PRIOR walks tutor.mentor_id → tutor.user_id — the self-referencing FK is exactly the recursive relationship the ERD rubric grades by name.

6. Set operator — everyone tied to one module

Lecture 6 · Relational Algebra (∪) Console

List everyone connected to "SQL Fundamentals" — learners enrolled in it and tutors teaching it — as one combined list.

SELECT au.full_name AS person, 'LEARNER' AS role_in_module
  FROM enrollment e
  JOIN learner l   ON l.user_id = e.user_id
  JOIN app_user au ON au.user_id = l.user_id
  JOIN module m    ON m.module_id = e.module_id
 WHERE m.module_title = 'SQL Fundamentals'
UNION
SELECT au.full_name, 'TUTOR'
  FROM module_tutor mt
  JOIN app_user au ON au.user_id = mt.user_id
  JOIN module m    ON m.module_id = mt.module_id
 WHERE m.module_title = 'SQL Fundamentals'
 ORDER BY person;

UNION combines two differently-sourced row sets (enrolled learners, assigned tutors) into a single relation — the set-union operator from relational algebra, made concrete.

7. Aggregate + GROUP BY/HAVING — struggling modules

Lecture 6/7 · Aggregation Console

Which modules have more than two learners enrolled but an average progress below 60%?

SELECT m.module_title,
       COUNT(e.user_id) AS enrolled_learners,
       ROUND(AVG(e.progress_score), 1) AS avg_progress
  FROM module m
  JOIN enrollment e ON e.module_id = m.module_id
 GROUP BY m.module_title
HAVING COUNT(e.user_id) > 2 AND AVG(e.progress_score) < 60
 ORDER BY avg_progress;

HAVING filters on the aggregate itself (average progress), something WHERE can't do since it runs before grouping.

8. Window function — ranking learners within each module

Lecture 7 · Query Processing (advanced SQL) Console

Within each module, who's furthest along?

SELECT m.module_title, au.full_name AS learner, e.progress_score,
       RANK() OVER (PARTITION BY e.module_id ORDER BY e.progress_score DESC) AS rank_in_module
  FROM enrollment e
  JOIN module m    ON m.module_id = e.module_id
  JOIN learner l   ON l.user_id = e.user_id
  JOIN app_user au ON au.user_id = l.user_id
 ORDER BY m.module_title, rank_in_module;

RANK() OVER (PARTITION BY ...) — an analytic function computed per module without collapsing rows the way GROUP BY would.

9. OLAP rollup — progress by difficulty and status

Lecture 9 · Data Warehouse (OLAP) Console

Average progress by module difficulty and enrollment status, with subtotals per difficulty and a grand total.

SELECT m.difficulty, e.status,
       ROUND(AVG(e.progress_score), 1) AS avg_progress,
       COUNT(*) AS enrollments
  FROM enrollment e
  JOIN module m ON m.module_id = e.module_id
 GROUP BY ROLLUP(m.difficulty, e.status)
 ORDER BY m.difficulty NULLS LAST, e.status NULLS LAST;

GROUP BY ROLLUP(...) produces multi-level subtotals in one pass — the same OLAP roll-up operation the data warehouse lecture covers, run directly against module/enrollment treated as a mini fact table.

10. Transaction demo — atomicity via COMMIT/ROLLBACK

Lecture 5 · Transaction Management (ACID) SQL*Plus / SQL Developer only

Prove a change is undone in full if the transaction is rolled back — nothing half-applies.

-- 1. inspect current progress for one module
SELECT user_id, progress_score
  FROM enrollment
 WHERE module_id = (SELECT module_id FROM module WHERE module_title = 'SQL Fundamentals');

-- 2. bump everyone's progress in that module
UPDATE enrollment
   SET progress_score = LEAST(progress_score + 10, 100)
 WHERE module_id = (SELECT module_id FROM module WHERE module_title = 'SQL Fundamentals');

-- 3. re-run step 1's SELECT here to show the (uncommitted) change

ROLLBACK;

-- 4. re-run step 1's SELECT again -- back to the original values

Not a rubric requirement for the console (which is deliberately read-only), but the clearest live demonstration of atomicity: the UPDATE is visible mid-transaction, then ROLLBACK discards it completely — nothing the app's own queries ever show on their own.

14Validation performed & known limitations

No live Oracle connection was available while building this port. Everything below was validated without one; the actual data path (a real query hitting the CIKGU schema) has not been exercised by the person/tool that wrote this code. Run it once against your own oracle23ai container and click through the main flows (register, enroll, mentorship, console) before treating it as final.

What was checked

  • python -m py_compile on every .py file — no syntax errors.
  • python manage.py check — Django's system-check framework passes clean (settings, URLconf, template engine config).
  • Every template under cikguapp/templates/ parsed successfully via django.template.loader.get_template() — catches malformed {% %} tags.
  • Every named URL in cikguapp/urls.py resolved via django.urls.reverse(), including the parameterized ones (goal/module/tutor ids) — catches typos in {% url %} tag names and argument counts.
  • /login/ and /register/ rendered end-to-end through the full middleware + context-processor + template-inheritance stack via Django's test client (the only two pages that need no database row to render) — both returned 200 OK, including the CSS/Chart.js static-file URLs resolving correctly.
  • Unauthenticated requests to / and to a role-protected route (/learner/dashboard/) correctly redirect to /login/.

What wasn't checked

  • Any view that queries Oracle — every repository function, every dashboard, the SQL console, registration, and the two transaction demos are untested against real data.
  • Whether bcrypt.checkpw() actually accepts the exact hash strings Spring's BCryptPasswordEncoder wrote for the seeded accounts (they should — both are standard $2a$/$2b$ bcrypt — but this wasn't verified against the live app_user rows).
  • Concurrent-write behavior (the IntegrityError handling around duplicate enrollments/co-teacher assignments) — the code path exists but hasn't been triggered against a live constraint violation.
